## 二、为什么用 Pages 而不是 Worker

| 对比项 | Worker | Pages |
|--------|--------|-------|
| 能做 API 吗 | ✅ | ✅（Functions 底层就是 Worker）|
| 能托管网页吗 | ❌ 需要额外搞 | ✅ 自带 |
| 能用 D1/KV 吗 | ✅ | ✅ |
| Git 推送自动部署 | 需手动配置 | ✅ 自带 |
| 预览环境 | 需手动搞 | ✅ 每个分支自动生成 |
| 适用场景 | 纯后端服务 | 后端 + 前端在一起 |

**结论：** 我们这个项目既有网页（Dashboard）又有 API，用 Pages 一个项目就搞定，省事。

## 三、后端设计

### 3.1 技术选型

| 用途 | 工具 | 说明 |
|------|------|------|
| 后端框架 | Hono | 轻量 Web 框架，写 API 方便 |
| 数据库 | Cloudflare D1 | 存聊天记录、联系人、人设 |
| 配置存储 | Cloudflare KV | 存模型参数（换模型不用改代码）|
| 大模型 | DeepSeek Chat | 默认，可随时换成别的 |
| 部署 | Cloudflare Pages | Git 推送自动部署 |

### 3.2 API 接口清单

| 接口 | 方法 | 做什么 |
|------|------|--------|
| /api/chat | POST | App 把新消息发过来，后端调 LLM 生成回复并返回 |
| /api/chat/history | GET | 查某个会话的聊天记录 |
| /api/contacts | GET/POST | 管理联系人白名单 |
| /api/persona | GET/PUT | 读写人设配置 |
| /api/config | GET | 获取当前模型配置（App 启动时同步） |
| /api/status | GET | 健康检查 |

### 3.3 数据库表

**chat_history（聊天记录）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | 自增 | 主键 |
| platform | 文本 | Soul / QQ / 陌陌 / 连信 |
| contact_id | 文本 | 对方是谁 |
| contact_name | 文本 | 对方昵称 |
| role | 文本 | user（对方说的）/ assistant（AI回的） |
| content | 文本 | 消息内容 |
| created_at | 时间戳 | 什么时候发的 |

**contacts（联系人）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | 自增 | 主键 |
| platform | 文本 | 哪个平台 |
| contact_name | 文本 | 对方昵称 |
| is_whitelisted | 布尔 | 是否在白名单里 |
| notes | 文本 | 备注 |

**personas（人设）**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | 文本 | 人设标识（如 "male"、"female"）|
| name | 文本 | 显示名称（如 "阿杰"、"小夏"） |
| system_prompt | 文本 | 人设提示词 |
| is_active | 布尔 | 当前在用哪个 |

### 3.4 调用 LLM 的流程

`
App发来消息
    ↓
查 D1 获取最近 20 轮历史（超出的自动摘要）
    ↓
查 KV 获取当前模型配置和人设
    ↓
拼 prompt：人设 + 历史 + 新消息
    ↓
调 DeepSeek API
    ↓
拿到回复后存 D1
    ↓
返回回复给 App
`

## 四、Android App 设计

### 4.1 技术选型

| 用途 | 工具 |
|------|------|
| 开发语言 | Kotlin |
| UI 框架 | Jetpack Compose |
| 本地数据库 | Room |
| 网络请求 | OkHttp |
| 无障碍服务 | AccessibilityService |
| 通知监听 | NotificationListenerService |

### 4.2 核心模块

**无障碍服务（AccessibilityService）**
— 这是 App 的"手"和"眼"。能读取其他 App 的界面内容，能模拟点击、输入、滑动。

**通知监听（NotificationListenerService）**
— 这是 App 的"耳朵"。有新消息时系统通知栏会弹出，我们的 App 能读到通知内容，不用一直轮询。

**工作流程：**

`
收到通知（NotificationListener）
    ↓
判断是不是目标 App（Soul/QQ/陌陌/连信）
    ↓ 是
通知无障碍服务：跳转聊天页面
    ↓
读取聊天内容
    ↓
发给云端 API 获取 AI 回复
    ↓
模拟操作：粘贴回复 → 点击发送
    ↓
返回消息列表，等待下一个通知
`

### 4.3 人工接管设计

| 操作 | 效果 |
|------|------|
| 点悬浮窗 | 立即暂停 AI 托管 |
| 手指碰屏幕任何位置 | AI 检测到用户操作，主动停止 |
| 通知栏开关 | 一键开/关托管 |
| 写入门禁模式 | AI 只粘贴不发送，你审核后手动点发送 |

### 4.4 保活策略

三层保活确保 App 不会被系统杀掉：

1. **通知栏常驻** — 前台服务，系统不会随便杀
2. **悬浮窗** — 额外一层前台标记
3. **开机自启** — 重启后自动恢复

## 五、安全设计

| 机制 | 实现方式 |
|------|----------|
| API 鉴权 | 每个请求带 Token，后端验证 |
| 防重复回复 | 同一条消息 ID 5 分钟内不重复处理 |
| 联系人白名单 | 只回复白名单里的人 |
| 超时保护 | 单次操作 150 秒超时自动放弃 |
| 违规弹窗处理 | 检测封号/禁言弹窗自动关闭 |
| 消息加密 | 聊天记录存 D1 前加密，读回时解密 |

## 六、实施顺序

建议分四步走：

| 步骤 | 内容 | 预计工作量 |
|------|------|-----------|
| **1. 搭后端** | Pages + D1 + KV + API 接口 | 先做 |
| **2. 写 App 核心** | 无障碍服务 + 通知监听 + 调 API | 其次 |
| **3. 联调跑通** | Soul 平台端到端跑通 | 再其次 |
| **4. 扩展** | 加 QQ/陌陌/连信 + Dashboard | 最后 |

**先跑通一个平台（Soul），再复制到其他三个，而不是同时做四个。**

## 七、Dashboard 管理面板

网页管理后台，放在同一个 Pages 项目里：

- 查看聊天记录（按平台、联系人筛选）
- 管理人设（增删改查、切换当前人设）
- 管理联系人白名单
- 切换模型配置（改 API Key、模型名、Base URL）
- 查看统计（回复数、活跃联系人）
