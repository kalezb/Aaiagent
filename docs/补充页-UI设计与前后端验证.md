# 补充页 - UI 设计与前后端验证

> 所有按钮都有触控反馈，开关状态用颜色区分，前端改配置后端必须验证收到并执行。

---

## 一、通用设计规范

### 1.1 颜色规范

| 状态 | 颜色 | 说明 |
|------|------|------|
| **开启/已授权/正常** | 绿色 #4CAF50 | 开关滑块在右，按钮背景绿色 |
| **关闭/未授权/暂停** | 灰色 #9E9E9E | 开关滑块在左，按钮背景灰色 |
| **异常/错误/失败** | 红色 #F44336 | 红闪烁，错误提示文字 |
| **强调/主按钮** | 蓝色 #2196F3 | 主要操作按钮，蓝色背景白字 |
| **次要/次要按钮** | 白色背景灰边 | 次要操作按钮，白底灰边 |

### 1.2 触控反馈（所有按钮必须有）

| 反馈类型 | 触发条件 | 效果 |
|---------|---------|------|
| **短震动** | 点任何按钮 | 10ms 短震动，确认点到了 |
| **按钮按下动画** | 点按钮时 | 按钮缩小 95%，松开恢复 |
| **开关切换动画** | 拨动开关 | 滑块平滑滑动 200ms，颜色渐变 |
| **成功提示** | 操作成功 | Toast 绿色文字"已保存" |
| **失败提示** | 操作失败 | Toast 红色文字"保存失败，请重试" |

## 七、前后端验证机制（关键！）

### 7.1 为什么要验证？

**前端改了配置，后端必须确认收到并且真的执行了。**
不然前端显示"已开启托管"，后端根本没收到，白高兴一场。

### 7.2 验证流程

```
用户在前端改配置
  ↓
前端发请求到后端 /api/config/save
  ↓
后端保存到 D1 数据库
  ↓
后端返回 { "success": true, "data": 刚保存的配置 }
  ↓
前端对比：后端返回的配置 == 前端发出去的配置？
  ↓
  ├─ 是 → 显示 Toast "已保存"，开关保持新状态
  └─ 否 → 显示 Toast "保存失败"，开关弹回原来状态
```

### 7.3 代码示例

```kotlin
// 前端：保存配置
suspend fun saveConfig(config: AppConfig): Boolean {
    // 1. 发请求
    val response = api.saveConfig(config)
    
    // 2. 验证后端返回的数据
    if (response.success && response.data == config) {
        // 3. 后端确实保存了
        Toast("已保存")
        return true
    } else {
        // 4. 后端没保存成功，UI弹回原来状态
        Toast("保存失败，请重试")
        switchBackToOldState()
        return false
    }
}
```

|--------|-----------|

## 八、错误处理

| 错误场景 | 处理方式 |
|---------|---------|
| 网络不好，保存失败 | Toast红色"网络不好，保存失败"，开关弹回 |
| 后端返回的配置和前端发的不一样 | Toast"配置不一致，请重试"，开关弹回 |
| 后端500错误 | Toast"服务器错误，请稍后再试"，开关弹回 |
| 保存超时（3秒没响应） | Toast"超时了，请重试"，开关弹回 |

## 九、总结

1. **所有按钮都有触控反馈**：短震动 + 动画
2. **开关状态用颜色区分**：绿色=开，灰色=关，红色=异常
3. **前端改配置，后端必须验证收到并执行**
4. **验证失败，UI弹回原来状态**，不能显示假的"已开启"
